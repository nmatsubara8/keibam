# JRDB TARGET ダウンロードデータ 解析台帳

新モダリティ検証（STEP5）の入口。JRDB の TARGET 向けダウンロード（外厩/展開/番手/IDM 馬印・
成績IDM・各ランク）が、市場と直交する私的情報として予測に効くかを、**実ファイルを1つずつ解析**して
見極めるための台帳。方針: ページ HTML を読むより、実際に落ちたファイルを解析する方が早い。

既存の JRDB 標準データ（KYI/SED/SKB…）とは別系統。取込基盤（`src/jrdb/`）は流用可能だが、
本データのレイアウトは未知のため、まずキー・列・形式を確定してから配線する。

- 認証: env `JRDB_USER`/`JRDB_PASS`。スクレイピング間隔 ≥4 秒。セッショントークンはコミット禁止。
- 解析ヘルパ: `python scripts/jrdb_target_probe.py <file.zip|.lzh|.txt|dir>` で Phase2-3 を自動出力。

## 解析フェーズの定義

- **Phase2 実ファイル解析**: filename / size / encoding / record数 / 改行コード。（`jrdb_target_probe.py` が出力）
- **Phase3 フォーマット解析**: 固定長 / CSV / TSV / SJIS/UTF-8。TARGET 向けは固定長 or `RaceID,HorseNo,印` の可能性。
- **Phase4 キー解析（最重要）**: `RaceID` / `開催+日+R+馬番` / `血統登録番号` のどれか。→ DB 結合方法が決まる。
  - 参考: 標準 JRDB の race_id 規則・血統登録番号(ketto) は `src/jrdb/_augment.py` / `_keys.py` を流用可能か検証。
- **Phase5 情報量解析**: 印（◎○▲△）だけか、`外厩名/帰厩日/放牧先` 等の構造化情報か。
  - JRDB 公式では競走馬データ(KY)側に「放牧先/入厩年月日/入厩何日前/入厩何走目」が入るとの説明あり
    （外厩の"素の情報"が別データにある可能性）。

## 解析メモ（実ファイル確定分・2026-07-31）

### 外厩馬印 `gaikyu_YYYYMMDD.zip`
- 内包 `場年回日R種別.DAT`（レース単位・例 `012612026.DAT` = 場01 年26 回1 日2 R02 種別6）。
- レコード = 固定長 10 バイト・cp932・CRLF: `[0:8] 血統登録番号(ASCII)` + `[8:10] 外厩コード(2byte)`。
  - 外厩コード = 2 半角（`NF`=ノーザンF, `CH`, `ST`, `YT`…）or 1 全角（`天`=天栄, `山`=山元, `鈴`…）。
- 結合キー = **血統登録番号(ketto)**。featured/JRDB は ketto を持つため直結可（`src/jrdb/_augment` 流用）。

### 外厩コメント `gaikyucomment_YYYYMMDD.zip`（ML 本命）
- 内包 `YC場年回日.DAT`（開催単位・全レース）。CSV・cp932・CRLF。
- レコード = `KEY,外厩名␣帰厩日␣中N週`。KEY(10桁) = `場(2)場+年(2)+回(1)+日(1)+R(2)+馬番(2)`（␣=全角空白）。
  - 例 `0426220104,ノーザンＦしがらき　07/07　中4週`。
- 結合キー = **(race_id, umaban)**。race_id 再構成 = `20YY + 場 + 回 + 日 + R`（netkeiba 12桁へは回/日を 2 桁ゼロ詰め）。
  既存 `attach(featured, ..., umaban_col="馬番")` の (race_id,馬番) 結合にそのまま乗る。
- 特徴量候補: `外厩名`(カテゴリ・放牧先の質)、`帰厩日`→今走までの日数、`中N週`(ローテ間隔)。
  市場織込みの有無は CI 下限>1.0 で検証（有名な「NF 天栄/しがらき」効果が市場と直交して残るか）。

### 番手/位置取り馬印 `itidori_YYYYMMDD.zip`
- 外厩馬印と同型: 内包 `場年回日R2.DAT`（レース単位・末尾 `2`=種別コード）・固定長 10B・cp932・CRLF。
  `[0:8]血統登録番号` + `[8:10]位置コード`（`最`最内/`内`/`中`/`外`/`大`大外＝予想走行レーン）。結合キー=ketto。
- **確定: ファイル名末尾1桁=データ種別コード**（外厩馬印=6, itidori=2）。馬印系は全て `[ketto][コード]` 固定長。

### IDM馬印 `idm_YYYYMMDD.zip`
- 内包 `場年回日R5.DAT`（レース単位・末尾5=種別・**6レコード固定=IDM上位6頭のみ**）・固定長10B・cp932。
  `[0:8]血統登録番号` + `[8:10]印(◎○▲△▽注)`。結合キー=ketto。**jrdb_idm から導出可＝新規情報なし**。

### 厩舎(調教師)ランク `tnrank_YYYYMMDD.zip` / 騎手ランク `jocrank_YYYYMMDD.zip`
- CSV・**utf-8**（馬印系 cp932 と異なる）。tnrank=CRLF、jocrank=LF。zip 内は単一 csv（開催非依存の年次/期間ランク）。
- tnrank: `区分,調教師コード(5),ランク,名前`（例 `2,01048,05,畠山吉宏`）。
- jocrank: `区分,騎手コード(4),ランク,名前`（例 `1,1181,12,秋山稔樹`）。区分 1=関東/2=関西 推定。
- 結合キー=調教師/騎手コード or 名前。featured の jockey/trainer 集計と重複気味だが JRDB 独自ランクは別軸の可能性。

### G1 結果（外厩 raw 特徴の本番採用検証・2026-07-31・NO-GO 確定）

`scripts/gaikyu_adoption_check.py`（本番 featured 570列 baseline vs +外厩・未来分割 2024 cutoff・
学習 521,619 / 評価 147,415・複勝）。myspeed_adoption_check と同方式。

| 構成 | ①ΔlogLoss | ①ΔAUC | ②年別改善 | ③placebo | ④利用馬のみΔLL | ⑤ECE |
|---|---|---|---|---|---|---|
| raw4（name あり） | **+0.00465**（悪化） | −0.00376 | 0/3 | +0.00397（≈実測） | +0.00158 | 悪化 |
| operational（name なし） | **+0.00222**（悪化） | −0.00149 | 0/3 | +0.00097 | **−0.00007（≈0）** | 悪化 |

- name(475水準の native categorical)は importance rank **1/574** なのに OOS 悪化＝**高カーディナリティ過学習**。
- has/days/weeks は importance ほぼ0（has=0, days=23, weeks=18）＝**570特徴 baseline に限界情報ゼロ**。
- name を外しても ΔlogLoss は正（悪化）、最も有利な④利用馬のみで ≈0。

**結論**: 外厩の運用情報（利用有無・帰厩鮮度・ローテ間隔・放牧先名）は **既存特徴
（`jrdb_nyukyu_days`/`jrdb_rotation` 等の休養・間隔系）＋市場に織り込み済みで、市場直交の純増分なし＝帰無**。
本命だった外厩も No-Go。→ 履歴集約・target encoding には進まず終了（#22 と同じ規律）。

## 最短の進め方（推奨）

次の 3 ファイルを 1 つずつ取得し `jrdb_target_probe.py` にかければ、URL規則・圧縮・文字コード・
レコード構造・キー・TARGET 取込形式との対応がほぼ解明できる:

1. 外厩馬印（日次）1 ファイル
2. 外厩コメント（日次）1 ファイル
3. 成績IDM（年次）1 ファイル ← 指数の可能性が高く最優先

出力を本台帳へ転記 → 残りは同手順で機械的に埋める。キー確定後、`CI下限>1.0` ハーネス
（`myspeed_adoption_check.py` 系）へ載せて「市場と直交する純増分があるか」を検証する。

## 検証規律（維持）

- 目的は確率品質（＋私的情報の直交性）。ROI 判定は必ず OOS＋placebo＋レース単位ブロック bootstrap CI 下限>1.0。
- スクレイピングはポライトネス ≥4 秒。JRDB セッショントークン/認証情報はコミット禁止。
- 「印」系は市場が既に織り込んでいる公算。**成績IDM 等の指数**が市場未織込の私的情報かを重点検証。
