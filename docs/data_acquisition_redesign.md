# データ取得項目の再設計 — 画面サンプル分析（作業中）

最終更新: 2026-06-21（画面サンプル 5 枚受領時点 / ユーザーが「これが最後」と言うまで追記継続）

netkeiba 画面で提供される項目を**極力多く**取得する方針に基づき、ユーザー提供の画面サンプルの
各項目を現行 raw スキーマと突き合わせ、取得方法と実装コストを分類する。

## 凡例（分類コード）

| コード | 意味 | 実装コスト |
|---|---|---|
| ✅ | 取得済み・特徴量で使用中 | 0 |
| 🟡 | raw HTML に取得済みだが未選択（FE で拾うだけ） | 低（処理層のみ） |
| 🟠 | 同一ページだが別テーブル等で**追加パーサが必要** | 中（パーサ追加） |
| 🔵 | **別ページの新規フェッチが必要** | 高（スクレイパ追加・取得時間増） |
| 🔒 | **プレミアム（P）＝要ログイン**。匿名スクレイパでは取得不可 | 要・ログイン基盤 |

> **横断的注意**: 画面の `P` アイコン項目は netkeiba プレミアム契約＋ログインセッションが
> 必須。現行の匿名 Playwright スクレイパでは空欄になる。これらを取るには別途
> 「ログイン対応」が前提（方針未確定）。

## 中間まとめ（サンプル①〜⑤時点）

### 無料で追加取得できる項目（ログイン不要・実装コスト 低〜中）
- **results（当該レース）**: タイム / 着差 / 通過 / 上り / 人気 / 賞金 / 馬名 〔🟡🟠〕
- **レース展開**: コーナー通過順位表 / ラップタイム・ペース表 〔🟠 追加パーサ〕
- **horse_info プロフィール**: 産地 / 獲得賞金 / 通算成績 / 主な勝鞍 / 近親馬 / セリ価格 〔🟡〕
- **horse_results**: 備考 / 勝ち馬(2着馬) 〔🟡〕

### プレミアム（要ログイン）— 別途方針が必要
- タイム指数 / 調教タイム / 厩舎コメント / 備考(race) / 馬場指数 / 馬場コメント /
  トラックバイアス / 適性レビュー / 走行データ詳細（タイム指数マスター・個別ラップ）

### 予測利用上の注意
- 当該レースの結果系（着順/タイム/上り/通過/ラップ）は**事後情報**。未来レースの予測には
  使えず、**過去走の特徴量（horse_results 経由）としてのみ**有効。horse_results は
  通過/上り/タイム/ペースを既に集計済み。
- レース展開（ラップ/ペース）は**レース質の事後ラベル**。コース×馬場別のペース傾向や、
  各馬の「速いペースでの実績」等に集計して特徴量化する余地あり。

## サンプル⑧⑨⑩: 調教師ページ `db.netkeiba.com/trainer/<trainer_id>` 【新ページ種別】

**現行では未取得**。results から `trainer_id` を取り、horse_results 集計で間接的に
調教師成績を作っている（リーク無し＝レース日時点まで）。このページは**集計済み成績**を直接提供。

| 画面項目 | 分類 | 備考 |
|---|---|---|
| プロフィール（出身地/デビュー年/所属） | 🔵 | 新ページ。静的属性 |
| 本年/通算 勝利数・獲得賞金 | 🔵⚠️ | 新ページ。**現在時点の累計＝過去学習にはリーク**。live 予測向け |
| GI/重賞 勝利数 | 🔵⚠️ | 同上 |
| 初出走/初勝利/初重賞/初G1 | 🔵 | 静的（デビュー実績） |
| リーディング情報（年度別順位） | 🔵 | 年度別なら as-of 集計でリーク回避可 |
| 直近5年成績（順位/着別度数/出走/勝率/連対率/複勝率/代表馬） | 🔵 | **無料**。年度別なのでリーク管理しやすい |
| データ分析: 騎手別勝利数（騎手相性） | 🔵 | **無料**。調教師×騎手の相性特徴の候補 |
| 続き（詳細成績） | 🔒 | プレミアム（登録/ログイン要） |

> **重要な論点**: 調教師/騎手ページの「累計成績」は**現在時点のスナップショット**であり、
> 過去レースの学習に使うと**未来情報リーク**になる。既存方式（horse_results からレース日
> 時点までを集計）はリーク無しで優れている。新ページの価値は主に
> ①**live 予測時の最新調教師調子**、②**年度別成績**（as-of でリーク回避可能）、
> ③**調教師×騎手相性**。コース別成績等は horse_results 集計の方が安全。

## C. リーク設計（最重要の横断ルール）
- **人物/血統の「累計・本年」成績はスナップショット＝未来情報リーク**。過去学習に使うと汚染。
  - ✅ **年度別成績を「当該レース年の前年まで」で as-of 結合** → リーク無し。
  - ✅ または既存方式（horse_results をレース日時点まで集計）を継続。
  - ⚠️ 「通算勝率」等を素で結合するのは厳禁。live 予測のみ最新値を別系統で使う。
- 調教/パドック/馬体重/出馬表はレース前に確定 → **リーク無し**（そのまま特徴化可）。

## C-2. 名寄せ（エンティティ解決）— 学習前の必須前処理 ⚠️

**ユーザー指摘**: 馬名・レース名・厩舎名・生産者名は**表記ゆれ**があるため、**テーブル化した上で
学習前に名寄せ**すべき。→ 全面的に妥当。設計に正式採用する。

### 原則: 「名前」でなく「ID」を正準キーにする
- netkeiba は各エンティティに**安定 ID**を持つ（horse_id / jockey_id / trainer_id /
  owner_id / breeder_id / race_id）。**結合・集計は常に ID で行う**（名前は表示専用）。
- 現状の支配特徴（owner/jockey/trainer）は既に ID エンコードで正しい。問題は
  **「名前しか無いフィールド」**で、これらは ID へ解決（名寄せ）してから特徴化する。

### 表記ゆれが実際に問題になる箇所
| データ | 表記ゆれの例 | 対策 |
|---|---|---|
| **生産者名** | 「ノーザンファーム」vs「ノーザンファーム 勇払郡」（所在地サフィックス付き） | breeder_id を正準キーに。名前は正規化（所在地除去）してマスタ化 |
| **馬主名** | 個人/クラブ法人の表記揺れ、全角半角、㈱有無 | owner_id を正準キー。**数値ID↔ハッシュID(`o_`)対応**も名寄せの一部 |
| **レース名** | 重賞改称・スポンサー名変更、クラス旧称(500万下→1勝) | race_id を正準キー。クラスは既存 `RACE_CLASS_LEGACY_ALIASES`。**重賞は系列ID(grade系列)へ正規化** |
| **馬名（テキスト参照）** | 調教「外アマイ馬也と併入」/ horse_results「勝ち馬」/ 近親馬/兄弟 は**名前断片のみ** | 馬名マスタ(horse_id↔馬名)で**名前→ID解決**。部分一致は要注意 |
| **騎手/調教師名** | 旧姓・改名、外国人騎手のカナ表記揺れ | jockey_id/trainer_id を正準キー |

### 名寄せレイヤの設計
1. **マスタテーブルを構築**（raw 取得時に蓄積）:
   - `horse_master`(horse_id, 正準馬名, 別名集合) / `person_master`(type, id, 正準名, 別名, 数値↔ハッシュ)
   - `race_master`(race_id, 正準レース名, grade, 系列キー, 開催)
2. **正規化関数**: 全角半角統一(NFKC)・空白除去・所在地サフィックス除去・記号正規化。
3. **名前→ID 解決**: 新規テキストフィールド（調教併入相手・勝ち馬・近親馬・パドック対象）は
   マスタ照合で ID 化。曖昧（同名・部分一致）はログして欠損扱い（誤結合より安全）。
4. **適用タイミング**: raw→featured の前段に「名寄せ正規化」ステップを置き、ID 解決済みの
   列だけを特徴量化に渡す。**学習前に確定**（推論時も同一マスタを適用し整合）。

> これは新規フィールド（特に調教の併入相手・近親・勝ち馬）を特徴化する際に必須。ID で
> 取れるものは ID 優先、名前しか無いものはマスタ経由で解決する二段構え。

## D. 実装方針（パーサ設計）
1. **人物共通パーサ** 1 本（`{jockey,trainer,owner,breeder}/result.html`）。
   - **数値ID↔ハッシュID対応**（owner=`o_`, breeder=`b_`）の解決を内蔵。
   - 出力: (entity_type, entity_id, year) × {芝/ダ × 平場/特別/重賞 の出走・勝利・各率}。
   - as-of 結合ヘルパ（race 年 → 前年までの累積/移動平均）。
2. **調教(oikiri)パーサ**: per-race 新規フェッチ。タイム(ラップ分解)→コース別標準化、
   脚色/評価/映像グレードをエンコード。odds と同程度の取得負荷（レース単位）。
3. **既取得フィールドの活性化**: 各 Processor の `_select_columns` 拡張のみ（Tier 1）。
4. **導出特徴**: horse_results から ローテ/距離変化/斤量増減/対戦/持ちタイム を算出。
5. **データソース抽象化との整合**: 新ページ取得は `AbstractRaceDataSource` の拡張
   （`acquire_training` 等）として追加し、netkeiba/jravan 切替の枠組みを維持。
6. **名寄せレイヤ**（C-2）: マスタ構築 + 正規化関数 + 名前→ID 解決。raw→featured の前段に配置。
   新規モジュール候補 `src/preprocessing/_entity_resolver.py`。
