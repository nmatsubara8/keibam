# 馬券戦略 — 単勝エッジと運用パラメータ

> # ⚠️ 重要（2026-06-29）: 以下の回収率は honest 再検証が必要
>

> 確率1.0で当てる（held-out 単独 AUC=1.0）。本ブランチのパイプラインは `rank_win` を

> そのまま信用しないこと。** 本ブランチの先進モデル（ベンター/Elo/r̂較正）も含め、エッジ主張は
> 移植済み `walk_forward.py`（時系列 OOS）で再検証してから扱うこと。**実戦投入は再検証まで禁止**。
> 経緯は blissful ブランチ §3-42 / 診断ツール `debug_leak.py`・`debug_backtest.py`。

このドキュメントは、本システムで（かつて）実運用を想定した馬券戦略の根拠・検証・運用手順を
まとめたもの。**⚠ 上記のとおり数値は再検証前提**。

---

## TL;DR

- **戦略**: 単勝・**EV > 1.1**・**オッズ ≤ 15 倍**。フラクショナル・ケリーで賭け金配分。
- **成績**: 2022–2026 の**全年度でフラット回収率 1.9–2.1**（確定オッズ基準・的中率 21–24%）。
- **設定**: [`config.yaml`](../config.yaml) に集約。当面は `advisory`（推奨表示のみ）・保守的な 1/4 ケリー。
- **実戦の留保**: 払戻はパリミュチュエルで確定オッズどおり（=正しい）。残る近似は**選定時に
  暫定オッズを使う点のみ**で、暫定≈確定のため影響は限定的（§6）。

## 1. 背景 — なぜこの戦略にたどり着いたか

モデルは ID 記憶が支配的（馬・騎手・種牡馬等）で、特徴量追加は頭打ちだった。
血統データの大規模 DL（約 23 時間）を検討したが**中止**し、「特徴量を増やす」以外の打ち手を
コードに即して探索した結果、**伸びしろはモデルではなく『賭け方』**にあると判明した。

**否定された打ち手（やらないこと）**:

| 打ち手 | 検証結果 |
|---|---|
| 特徴量追加（血統含む） | 頭打ち。寄与ほぼ0 |
| 券種スイッチ（複勝/ワイド/馬連…） | 単勝が断トツ。複勝0.81・ワイド0.64 と劣る |
| 控除率較正（calibration） | Δ回収率 ≤ 0.009 で誤差 |

→ 残った唯一のレバーが**単勝の「オッズ絞り込み × ベットサイジング」**。

## 2. エッジの実在性検証（`validate_edge.py`）

単勝 EV エッジが「本物の予測力」か「オッズ選択の副産物（人気薄バイアス）」かを切り分けた。

**閾値スイープ（本番モデル）**: EV 閾値を上げると回収率が単調上昇 — 真のエッジの兆候。

| EV閾値 | 1.10 | 1.30 | 1.80 | 2.20 | 3.00 |
|---|---|---|---|---|---|
| 回収率（本番） | 1.013 | 1.155 | 1.661 | 2.170 | **3.718** |
| 回収率（プラセボ） | 0.631 | 0.633 | 0.618 | 0.606 | 0.595 |

**プラセボ（レース内で予測勝率をシャッフル）は全閾値で 0.6 前後フラット**。本番との差が
モデルの純粋な予測力であり、「人気薄バイアスの副産物」説は否定された。

**リーク監査**: 結果系を疑う特徴量を個別にコード確認し、すべて潔白を確認した。

| 特徴 | 判定 | 根拠 |
|---|---|---|
| `owner_avg_rank` | ✅ | `shift(1)` で現レースを除外した過去走平均 |
| `wet_rel_rank` | ✅ | `date < target_date` の過去走のみ |
| `単勝_z` 等 | ✅ | 確定オッズ由来＝**締切直前に入手可能**（結果由来でない） |

## 3. エッジの所在 — オッズ帯別（`kelly_backtest.py` の診断）

エッジは**人気薄ではなく中人気（3–15倍）に集中**する。15 倍超は -EV のジャンク。

| オッズ帯 | 買い目 | 的中率 | 回収率 |
|---|---|---|---|
| 1–3 | 8 | 0.875 | 2.350 |
| **3–7** | 1,634 | 0.654 | **3.670** |
| **7–15** | 12,178 | 0.177 | **1.777** |
| 15–50 | 35,765 | 0.040 | 0.996 |
| 50+ | 47,033 | 0.008 | 0.735 |

`EV > 1.1` だけだと候補の **86%（15倍超）が分岐点〜赤字**の人気薄で占められ、フラットベットは
**破産する**（無フィルタ時の回収率 0.963）。**オッズ ≤ 15 倍フィルタが戦略の核心**で、これだけで
負け戦略が 2 倍戦略に反転する。

特定年の偶然ではない。

## 5. 運用パラメータ（[`config.yaml`](../config.yaml)）

| パラメータ | 値 | 根拠 |
|---|---|---|
| `operation_mode` | `advisory` | 当面は推奨表示のみ（発注は人間） |
| `bankroll` | 100,000 | 元手 |
| `tansho_ev_threshold` | **1.1** | 単勝 EV 下限（既定 `BetThresholds.TANSHO=1.78` を上書き） |
| `max_odds` | **15.0** | これ超のオッズ（人気薄）は買わない |
| `kelly_fraction_ratio` | **0.25** | 実現性未検証のため保守的な 1/4 ケリー（§6） |
| `per_bet_cap_ratio` | 0.05 | 1 馬券 ≤ bankroll の 5% |
| `max_daily_loss_ratio` | 0.3 | 当日損失が 30% 超で kill switch |

配線箇所: `app/_prediction_service.py` の `run_prediction` が `tansho_ev_threshold`（EV 閾値の
上書き）と `max_odds`（選定後のオッズ上限フィルタ）を適用する。`OperationConfig` のコード既定は
無害（`max_odds=inf` / `tansho_ev_threshold=None`）で、実値は `config.yaml` 側で与える。

## 6. 締切前オッズと確定オッズの差 — 限定的な近似

**重要な前提**: JRA は**パリミュチュエル方式**。払戻は締切後に確定する**確定オッズ**で決まり、
ベット時に表示される暫定オッズで固定されるわけではない（ブックメーカーの固定オッズと異なる）。
勝てばベット時のオッズが何であれ確定オッズで支払われる。
→ **バックテストが払戻に確定オッズを使うのは「楽観」ではなく「正しい」。** それが実際に受け取る倍率。

残る近似は**選定（どの馬を買うか）だけ**である:

- 決定時点では暫定オッズしか見えず、それで EV>1.1・オッズ≤15 を判断する。
- **暫定オッズ ≈ 確定オッズ**（流動性の高いレースの締切数分前）なら、選ぶ馬集合はほぼ変わらず、
  払戻は確定オッズ（=正しい）なのでエッジはほぼ保たれる。

二次的に残る論点（いずれも限定的）:

1. **train/serve skew** — モデルは特徴量 `単勝_z`（確定オッズ）で学習。実戦では暫定オッズを
   入力するため僅かにずれる。
2. **境界付近の馬** — オッズ 15 倍近辺・EV 1.1 近辺は暫定↔確定の差で採否が入れ替わりうる
   （エッジ本体の 3–7 倍は境界から遠く堅牢）。
3. **late money 依存の可能性** — もしエッジが「締切直前にオッズが動く馬」を捉えているなら、
   決定時点では同じ信号が無く目減りする。これだけはスナップショット無しでは判別不能
   （`check_snapshot_coverage.py`: 締切前スナップショット **0 件**）。

→ 実戦リスクは「2.0 が大きく崩れる崖」ではなく**緩やかな目減り**の可能性。それでも未実証の
ライブ・エッジに対する通常の保守として `kelly_fraction_ratio = 0.25`（1/4 ケリー）を採る。

**前向き検証の目的**は、この目減り幅の定量化と late money 依存の有無の確認:

1. 締切前オッズを日次収集（数週間〜2 ヶ月蓄積）:
   ```bash
   python -m src.preparing.odds_scheduler --auto --window-minutes 60
   ```
2. `advisory` モードで戦略を稼働し、「何を・いくらで買うはずだったか」を記録。
3. 蓄積後、暫定オッズで選定 → 確定オッズで払戻、として回収率を再評価し、目減り幅を確定。

## 7. 運用手順

- **日常**: `operation_mode: advisory` で「🎯 予測・推奨」を確認 → カート → 「🛒 発注」。
  推奨は本戦略（単勝・EV>1.1・オッズ≤15）どおりに絞られる。詳細フローは
  [README 4-5](../README.md#4-5-馬券発注フロー)。
- **清算**: レース結果取込後に「🧾 結果で清算する」で実回収率・的中を自動集計。
- **前向き検証**: §6 のとおり `odds_scheduler` を cron 化し、締切前オッズを蓄積。
